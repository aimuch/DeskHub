## 1. 现在怎么配对

1. 电脑上运行 `deskhub-agent pair <设备编号>`。Agent 生成一个令牌，只把它的哈希存进数据库，把令牌写进权限 0600 的私有文件。
2. 用 USB 线连设备，运行 `tools/provision.py`。它读私有文件，把 Wi-Fi、Agent 地址、CA 和令牌写进设备。
3. 设备用令牌向 Agent 的 `/api/v1/device/sync` 上报。

这一套保留，不动。管理台“访问管理”页的“配对新设备”只是把这条命令写给用户看，不需要新接口。

## 2. 要解决什么

不接 USB 线，也能配对：人在设备旁边，用手机连设备自己的热点，在配网页里输入信息。

不做：
- 设备接入局域网后开放配网页。
- 默认密码，或不带时限的配对。
- 管理台直接显示或下发设备令牌。令牌只出现在 Agent 和设备之间。

## 3. 两个验证码，不要混

| 名字 | 谁生成 | 显示在哪 | 证明什么 |
| --- | --- | --- | --- |
| 配网码 | 设备 | 设备屏幕（设计稿 Dev-Pairing） | 手机的主人在设备旁边（R7 第 3 条） |
| 配对授权码 | Agent | 管理台，只显示一次 | 管理员同意这台设备加入这个 Agent |

## 4. 流程

1. 管理员在管理台点“配对新设备”，选权限范围和显示器目标，点“生成授权码”。
2. Agent 生成一个授权：8 个字符的公开授权编号，加 10 个字符的秘密授权码，字母表去掉易混的字符（0-9 和 A-Z，去掉 I、L、O、U）。有效 5 分钟，只能用一次。Agent 只存授权编号、授权码的加盐哈希、权限范围、目标、过期时间和剩余尝试次数。
   管理台显示一个**配对包**，只显示这一次。配对包是一串文本，约 120 个字符，复制粘贴即可：`DHP1.` 加上下面内容的 base64url（不带填充）。
   内容：版本字节 `01`，Agent 地址长度（1 字节），Agent 地址（`https://主机[:端口]`），授权编号（8 字符），授权码（10 字符），Agent 的 CA 指纹（32 字节，CA 证书 DER 的 SHA-256），校验（前面全部字节的 SHA-256 的前 4 字节）。校验用来发现复制时丢字符，不是安全措施。
3. 人长按设备按键 3 秒（或设备还没配对时自动开启）。设备开热点，屏幕显示配网码和倒计时（默认 5 分钟）。
4. 手机连热点（热点密码显示在设备屏幕上），打开配网页，输入配网码，再输入 Wi-Fi 名称、Wi-Fi 密码，并粘贴配对包。Agent 地址、授权编号、授权码和 CA 指纹都在配对包里，不用另外输入。
5. 设备连上 Wi-Fi。它手里只有 CA 指纹，没有 CA，所以分两步：
   a) 先向 `GET /api/v1/pairing/ca` 取 CA 证书。这一步的 TLS 连接还无法验证，所以这一步**不发送、也不接受任何秘密**：CA 是公开数据。设备计算收到的证书 DER 的 SHA-256，**必须等于配对包里的 CA 指纹**，不一致就中止，什么都不保存。
   b) 指纹一致后，设备把这个 CA 当作唯一信任根，重新建立 TLS 连接，检查证书链、主机名和有效期。通过之后才提交授权码。
   **第 5 步 a) 的“不验证 TLS”在 ESP-IDF 6.0.2 里没有安全的现成做法，建议改成配对包直接带 CA，见第 11 节，等你确认。**
6. 设备提交授权码。Agent 校验通过，生成每设备令牌，返回令牌和 CA。设备再核对返回的 CA 仍是被固定的那一份。授权码立刻作废。
7. 设备把 Wi-Fi、Agent 地址、CA、令牌，经和 USB 配对同一条保存路径写入（K1、K4 照旧），读回确认，再关热点。

## 5. Agent 的接口

| 接口 | 谁调用 | 作用 |
| --- | --- | --- |
| `POST /api/v1/admin/pairing-grants` | 管理员会话 + CSRF | 生成授权码。请求：权限范围、目标、有效秒数（最长 300）。响应：授权码（仅此一次）、过期时间、CA 指纹 |
| `GET /api/v1/admin/pairing-grants` | 管理员会话 | 列出授权：状态（待用、已用、过期、取消、已烧毁）、创建时间。不返回授权码 |
| `DELETE /api/v1/admin/pairing-grants/{id}` | 管理员会话 + CSRF | 取消 |
| `GET /api/v1/pairing/ca` | 设备，无令牌 | 取 CA 证书和它的指纹（公开数据，只接受 HTTPS，与兑换共用限流；不依赖任何授权） |
| `POST /api/v1/pairing/redeem` | 设备，无令牌 | 兑换：请求带授权编号、授权码和设备编号。成功返回 Agent 编号、令牌、CA、权限范围和目标 |

Agent 的配置新增两项：`pairing_ca`（CA 证书文件，只含公开证书）和 `public_url`（设备用来连 Agent 的 `https://主机[:端口]`）。缺任何一项，或 CA 文件不是证书，生成授权时返回 409，因为没有 CA 就没法让设备固定指纹（K1）。
授权最多带 `read:status`、`control:displays`、`device:sync`，**不能带 `admin:config`**：设备不能得到管理权限。显示器目标必须是已配置的显示器，不接受 `*`。同时待用的授权最多 8 个。
授权的状态：待用、已用、已取消、已烧毁；“已过期”由时间推出。授权编号对不上、授权码错、已过期、已用、已取消、已烧毁、设备编号与授权指定的不符，兑换都返回同一个 403 `PAIRING_REJECTED`。授权码错或设备编号不符扣一次尝试；已过期、已用、已取消、已烧毁、编号不存在不扣。
兑换先把授权标记为已用并提交，再签发令牌：中间崩溃只会浪费一个授权，不会让同一个授权签发两次。已配对设备在没有 `replace` 时，在标记之前就拒绝，授权不消耗。

兑换接口是唯一不需要登录的写接口，所以单独限制：
- 只接受 TLS 连接。
- 每个授权最多 5 次尝试，用完就烧毁，之后同一个授权码也不再有效。
- 按来源 IP 限流。限流器出错时拒绝，不放行（K1）。
- 授权码用常量时间比较；错误授权码、过期、已用、已烧毁，返回同样的错误和同样的耗时，不泄露区别。
- 设备编号必须符合格式，已配对的设备编号只有授权写明 `replace` 时才能兑换。
- 令牌只出现在这次响应里，不进日志，不进数据库（只存哈希）。

## 6. 信任链（K1）审查点

1. **第一次连接信谁。** 设备还没有 CA。方案是用 CA 指纹做固定：人从管理台抄来指纹，设备核对。这样热点上的攻击者即使伪造 Agent，也过不了指纹。缺点：指纹是 64 个十六进制字符，手机上输入容易错。选项见第 8 节。
2. **热点本身。** 热点用 WPA2，密码显示在设备屏幕上，每次开启重新生成。热点内只开配网页，不转发到局域网。
3. **手机到设备这一段不是 TLS。** 所以页面里输入的 Wi-Fi 密码和授权码有被同热点的人窃听的风险。热点用 WPA2、每次随机密码、限时、只有一台手机能连，把这个风险缩小到“在设备旁边、在 5 分钟内、知道屏幕上的密码”。授权码即使被窃听，没有 CA 指纹对应的真实 Agent 也无法兑换成令牌（兑换发生在设备和 Agent 之间，不经手机）。
4. **授权码泄露。** 5 分钟、一次性、5 次尝试。泄露后管理员可以取消。
5. **替换已有设备。** 默认拒绝。管理员要明确勾选“替换”，并且知道旧令牌会立即吊销。
6. **配网页的输入。** 全部严格校验：SSID 长度、密码长度、URL 只能是 https 加主机名，不能带路径、查询、用户名；沿用 `provision.py` 的同一套校验。

## 7. 失败模式（实现前要先写成测试）

Agent 端：
1. 授权码过期、已用、已取消、已烧毁、从没存在：兑换都失败，错误和耗时一致。
2. 第 6 次尝试：失败，且授权烧毁，即使第 6 次的码是对的。
3. 并发兑换同一个授权码：只有一个成功，令牌只发一个。
4. 兑换后重启 Agent：授权仍是已用，不能再兑换。
5. 权限范围、目标超出授权：拒绝。授权创建时就拒绝未知范围和空目标（沿用 `Store.pair` 的校验）。
6. 已配对的设备编号：没有 `replace` 就拒绝，且授权不消耗。
7. 限流器故障：拒绝。
8. 令牌不出现在日志、数据库明文、授权列表、错误信息里。
9. 有效秒数 0、负数、超过 300：拒绝。

设备端：
10. 配网码错误：不接受任何输入，错误 5 次关闭热点。
11. 热点 5 分钟到：关闭，输入的内容丢弃，什么都不保存。
12. 连不上 Wi-Fi、连不上 Agent、指纹不一致、证书过期、主机名不符：中止，旧配置原封不动。
13. 兑换成功但保存失败或读回不一致：不关闭配对状态，显示错误，旧配置不变。
14. 中途断电：要么是旧配置，要么是完整的新配置，不会有一半。
15. 已经配对且没有长按按键：热点不开。

## 11. 取 CA 这一步的调查结论（2026-10-28）

问题：设备只有配对包里的 CA 指纹，要先拿到 CA，才能做验证过的 TLS。第 4 节的做法是先用一个**不验证证书**的 TLS 连接去 `GET /api/v1/pairing/ca`。这在 ESP-IDF 6.0.2 里能不能安全地做？

### 结论

**没有安全的现成办法。**

1. **esp-tls 的默认行为是拒绝。** 客户端配置里没有任何验证选项（没有 CA、没有证书包、没有全局 CA 库）时，`esp_tls_mbedtls.c` 返回 `ESP_ERR_MBEDTLS_SSL_SETUP_FAILED`。唯一的出口是 `CONFIG_ESP_TLS_SKIP_SERVER_CERT_VERIFY`（依赖 `CONFIG_ESP_TLS_INSECURE`）。它是整个固件的编译期默认：开了以后，任何一处忘记配 CA 的客户端都会悄悄不验证。本项目的 `sdkconfig.defaults` 明确写了 `CONFIG_ESP_TLS_INSECURE=n`，这是 K1 的底线，不能开。
2. **`crt_bundle_attach` 钩子能做到，但要改基线。** `esp_http_client` 允许传一个函数，它能改写 mbedTLS 的配置（改成不验证，或装自己的验证回调）。可是这条路要 `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE`，`sdkconfig.defaults` 也明确关了它（`=n`）。打开它要改基线文件（K7），并在固件里留一个故意不验证的函数。
3. **直接用 mbedTLS 代价最大。** mbedTLS 4 已经去掉了 `mbedtls_ssl_conf_rng`，要走 PSA；套接字读写、超时、错误都要自己写。
4. **握手里看不到 CA。** `tools/create_tls.py` 生成 RSA-2048 的 CA 和叶子证书，Agent 的 `tls_cert` 是叶子证书。设备在握手里只看到叶子，所以“核对证书链的根的指纹”做不到，只能单独去取 CA。

### 两个选项

| | D2：取 CA 并核对指纹（第 4 节原来的做法） | D1：配对包直接带 CA |
| --- | --- | --- |
| 做法 | 开证书包选项，写一个不验证的钩子，`GET /pairing/ca`，核对指纹，再用验证过的 TLS 兑换 | 配对包里放 CA 证书（DER，RSA-2048 约 800 字节）。设备直接用它做验证过的 TLS，一步到位 |
| 配对包长度 | 约 120 个字符 | 约 1200 到 1300 个字符，只能复制粘贴 |
| 固件里的不验证连接 | 有一个，要靠审查保证它不发送秘密 | 没有 |
| 基线文件 | 要改 `sdkconfig.defaults`（K7） | 不用 |
| Agent | 多一个公开接口（已实现） | 不需要这个接口（要删掉）；配对包改格式 |
| 失败环节 | 多一个（取 CA） | 少一个 |
| 主机测试 | 不验证的那一步没法在主机上测 | 全部可以在主机上测 |

**两者的信任是等价的。** 配对包本来就是信任根：它经过手机和热点，指纹和 CA 在同一个包里，能改一个的人也能改另一个。指纹只换来“包短”，不换来安全。D1 的信任来源和 USB 配对一样：CA 由人带过来。

### 建议：D1

理由：固件里不留任何不验证的连接，不动 `sdkconfig.defaults`，少一个公开接口，少一个失败环节，所有逻辑都能在主机上测。代价只是配对包变长，而你选“配对包复制粘贴”的原因就是不用手抄。

D1 要改的东西（等你确认后，先写测试再改）：
- 配对包升到版本 2：`02`，地址长度，地址，授权编号，授权码，CA 长度（2 字节），CA DER，校验。解码器检查 CA 是一个 DER 序列（开头 `30`，长度一致，最大 1500 字节）。
- Agent：生成授权时放入 `pairing_ca` 的 DER；删掉 `GET /api/v1/pairing/ca` 及其测试；协议向量重新生成。
- 设备：解码器同步；`Session` 少 `FetchingCa` 阶段，连上 Wi-Fi 后直接兑换；兑换响应里的 CA 必须和包里的 CA 是同一份（DER 逐字节相同）。
- 第 8 节第 2 条要改成“配对包直接带 CA”。**这改了你定的决定，所以等你确认。**

如果你仍想要短包，选 D2：要改 `sdkconfig.defaults`，我会把钩子写成只在取 CA 时使用、不发送任何请求头和请求体里的秘密，并要求你复审那几十行代码。

## 12. 设备端接线方案

不管选 D1 还是 D2，下面这些都一样。每一条都要先写失败模式和测试（能在主机上测的部分），再写代码，接线的代码要按 K1 复审。

1. **Wi-Fi 模式。** 现在 `core.cpp` 的 `network_start()` 只设 `WIFI_MODE_STA`。热点要 `WIFI_MODE_APSTA`，加 AP 网络接口，WPA2，密码来自 `Session::offer()`，最多 1 台设备连接。这改基线文件（K7）。
   **风险（要真机验证）：** 提交表单后，设备要连家里的 Wi-Fi。APSTA 下两个接口必须同一个信道，热点会跟着变，手机可能断开。所以结果显示在**设备屏幕**上，不依赖手机页面；页面在提交后提示“手机可能会断开”。
2. **配网页。** `esp_http_server`，HTTP（热点内没有 TLS），只绑定热点接口，只开 `GET /` 和 `POST /setup`，限制请求体大小（D1 约 2 KiB），`Cache-Control: no-store`，响应不回显任何秘密，不写日志。热点关闭时停止服务。
3. **兑换客户端。** 一次验证过的 `esp_http_client`：D1 用 `cert_der`（包里的 CA），保持主机名检查，不跟随重定向，响应上限沿用 16 KiB。把 esp-tls 的错误和 mbedTLS 的验证标志（过期、名称不符、不被信任）映射到 `Session` 的 `Tls`。Agent 的证书必须含配对包里的地址（IP 或主机名），这和 USB 配对的要求一样。
4. **`Sink` 的实现。** `current()` 和 `readback()` 用 `dh::secrets()`，`set_time()` 用 `dh::set_time_utc(utc, "manual")`，`commit()` 用 `dh::save_secrets()`，成功后同 USB 配对一样写 RTC 并 `network_reconfigure()`。
5. **随机数。** 热点密码和配网码用硬件随机数。ESP32 的随机数只有在射频子系统（Wi-Fi 或蓝牙）开着时才是真随机。所以 `Session::open()` 必须在 Wi-Fi 启动之后调用；未配置的设备如果 Wi-Fi 还没启动，要先启动它。
6. **按键。** BSP 没有按键定义（`BSP_CAPS_BUTTONS` 为 0）。BOOT 键通常接 GPIO0，但本板要用原理图核对；PWR 键据说接在电源芯片上，长按可能触发硬件关机，所以不选它（这一点我也没有核对）。**我没法从代码里确认，需要你给原理图，或确认用哪个键，真机验证前一律标“未验证”。**
7. **屏幕。** 把 `Session::offer()` 映射到 `dh::PairingInfo`（`ui_pairing_show`，已有）。配网页显示期间要保持亮屏，否则人看不到密码：界面定时器在配网页显示时刷新“最近活动”，夜间限亮等保护仍然生效（K5）。
8. **K1 复审清单。** 配网码、Wi-Fi 密码、授权码、令牌不进日志；配网页只在热点内可达；窗口、尝试次数、授权都有上限；保存只发生一次且完整；失败时旧配置原封不动；固件里没有不验证的 TLS（D1）或只有一个被审查过的（D2）。
9. **真机验证（等你说“刷”）。** 热点能连、配网页能打开、一次完整配对、Wi-Fi 信道切换时的表现、断电时旧配置不丢、10 分钟后热点确实关闭。
