规则 R7 写明：这个功能要先设计，再按 K1 审一遍，然后才实现。顺序是：先写 Agent 端的失败模式和测试，再实现 Agent 端；设备端实现前，代码要 K1 复审一次。
实现中发现一处设计缺口，已在第 4、5 节修正：授权码要配一个公开的授权编号，否则错误的授权码找不到它属于哪个授权，“5 次尝试”就没法按授权计数。

## 1. 现在怎么配对

1. 电脑上运行 `deskhub-agent pair <设备编号>`。Agent 生成一个令牌，只把它的哈希存进数据库，把令牌写进权限 0600 的私有文件。
2. 用 USB 线连设备，运行 `tools/provision.py`。它读私有文件，把 Wi-Fi、Agent 地址、CA 和令牌写进设备。
3. 设备用令牌向 Agent 的 `/api/v1/device/sync` 上报。

这一套保留，不动。管理台“访问管理”页的“配对新设备”只是把这条命令写给用户看，不需要新接口。

## 2. 要解决什么

不接 USB 线，也能配对：人在设备旁边，用手机连设备自己的热点，在配网页里输入信息。

不做：
- 设备接入局域网后开放配网页。
- 默认密码，或不带时限的配对。
- 管理台直接显示或下发设备令牌。令牌只出现在 Agent 和设备之间。

## 3. 两个验证码，不要混

| 名字 | 谁生成 | 显示在哪 | 证明什么 |
| --- | --- | --- | --- |
| 配网码 | 设备 | 设备屏幕（设计稿 Dev-Pairing） | 手机的主人在设备旁边（R7 第 3 条） |
| 配对授权码 | Agent | 管理台，只显示一次 | 管理员同意这台设备加入这个 Agent |

## 4. 流程

1. 管理员在管理台点“配对新设备”，选权限范围和显示器目标，点“生成授权码”。
2. Agent 生成一个授权：8 个字符的公开授权编号，加 10 个字符的秘密授权码，字母表去掉易混的字符（0-9 和 A-Z，去掉 I、L、O、U）。有效 5 分钟，只能用一次。Agent 只存授权编号、授权码的加盐哈希、权限范围、目标、过期时间和剩余尝试次数。
   管理台显示一个**配对包**，只显示这一次。配对包是一串文本，复制粘贴即可：`DHP2.` 加上下面内容的 base64url（不带填充）。RSA-2048 的 CA 约 1090 个字符。
   内容：版本字节 `02`，Agent 地址长度（1 字节），Agent 地址（`https://主机[:端口]`），授权编号（8 字符），授权码（10 字符），CA 长度（2 字节，高位在前），Agent 的 CA 证书（DER，最多 2048 字节，必须恰好是一个 DER 序列），校验（前面全部字节的 SHA-256 的前 4 字节）。校验用来发现复制时丢字符，不是安全措施。
   配对包**直接带 CA**，所以设备不需要先取 CA，也没有不验证证书的连接（见第 11 节）。
3. 人长按设备按键 3 秒（或设备还没配对时自动开启）。设备开热点，屏幕显示配网码和倒计时（默认 5 分钟）。
4. 手机连热点（热点密码显示在设备屏幕上），打开配网页，输入配网码，再输入 Wi-Fi 名称、Wi-Fi 密码，并粘贴配对包。Agent 地址、授权编号、授权码和 CA 证书都在配对包里，不用另外输入。
5. 设备连上 Wi-Fi。它把配对包里的 CA 当作唯一信任根，从第一个字节起就建立验证过的 TLS 连接：检查证书链、主机名和有效期。通过之后才提交授权码。没有任何未验证的连接。
6. 设备提交授权码。Agent 校验通过，生成每设备令牌，返回令牌和 CA。设备再核对返回的 CA 与配对包里的 CA 是同一份（DER 逐字节相同）。授权码立刻作废。
7. 设备把 Wi-Fi、Agent 地址、CA、令牌，经和 USB 配对同一条保存路径写入（K1、K4 照旧），读回确认，再关热点。

## 5. Agent 的接口

| 接口 | 谁调用 | 作用 |
| --- | --- | --- |
| `POST /api/v1/admin/pairing-grants` | 管理员会话 + CSRF | 生成授权码。请求：权限范围、目标、有效秒数（最长 300）。响应：配对包（仅此一次）、过期时间、CA 指纹（SHA-256，只给人核对；设备不用它）|
| `GET /api/v1/admin/pairing-grants` | 管理员会话 | 列出授权：状态（待用、已用、过期、取消、已烧毁）、创建时间。不返回授权码 |
| `DELETE /api/v1/admin/pairing-grants/{id}` | 管理员会话 + CSRF | 取消 |
| `POST /api/v1/pairing/redeem` | 设备，无令牌 | 兑换：请求带授权编号、授权码和设备编号。成功返回 Agent 编号、令牌、CA、权限范围和目标 |

Agent 的配置新增两项：`pairing_ca`（CA 证书文件，只含公开证书）和 `public_url`（设备用来连 Agent 的 `https://主机[:端口]`）。缺任何一项，或 CA 文件不是证书，生成授权时返回 409，因为没有 CA 就没法让设备验证 Agent（K1）；CA 的 DER 超过 2048 字节同样返回 409，因为配对包放不下。配对包没有单独的 CA 下载接口：CA 只随配对包，由人带过来。
授权最多带 `read:status`、`control:displays`、`device:sync`，**不能带 `admin:config`**：设备不能得到管理权限。显示器目标必须是已配置的显示器，不接受 `*`。同时待用的授权最多 8 个。
授权的状态：待用、已用、已取消、已烧毁；“已过期”由时间推出。授权编号对不上、授权码错、已过期、已用、已取消、已烧毁、设备编号与授权指定的不符，兑换都返回同一个 403 `PAIRING_REJECTED`。授权码错或设备编号不符扣一次尝试；已过期、已用、已取消、已烧毁、编号不存在不扣。
兑换先把授权标记为已用并提交，再签发令牌：中间崩溃只会浪费一个授权，不会让同一个授权签发两次。已配对设备在没有 `replace` 时，在标记之前就拒绝，授权不消耗。

兑换接口是唯一不需要登录的写接口，所以单独限制：
- 只接受 TLS 连接。
- 每个授权最多 5 次尝试，用完就烧毁，之后同一个授权码也不再有效。
- 按来源 IP 限流。限流器出错时拒绝，不放行（K1）。
- 授权码用常量时间比较；错误授权码、过期、已用、已烧毁，返回同样的错误和同样的耗时，不泄露区别。
- 设备编号必须符合格式，已配对的设备编号只有授权写明 `replace` 时才能兑换。
- 令牌只出现在这次响应里，不进日志，不进数据库（只存哈希）。

## 6. 信任链（K1）审查点

1. **第一次连接信谁。** 设备还没有 CA。方案是配对包直接带 CA：人从管理台复制配对包，粘贴到配网页，CA 由人带过来，和 USB 配对的信任来源一样。热点上的攻击者即使伪造 Agent，也拿不到被这个 CA 签发的证书。选项和理由见第 8 节、第 11 节。
2. **热点本身。** 热点用 WPA2，密码显示在设备屏幕上，每次开启重新生成。热点内只开配网页，不转发到局域网。
3. **手机到设备这一段不是 TLS。** 所以页面里输入的 Wi-Fi 密码和授权码有被同热点的人窃听的风险。热点用 WPA2、每次随机密码、限时、只有一台手机能连，把这个风险缩小到“在设备旁边、在 5 分钟内、知道屏幕上的密码”。授权码即使被窃听，没有这个 CA 签发的真实 Agent 也无法兑换成令牌（兑换发生在设备和 Agent 之间，不经手机）。
4. **授权码泄露。** 5 分钟、一次性、5 次尝试。泄露后管理员可以取消。
5. **替换已有设备。** 默认拒绝。管理员要明确勾选“替换”，并且知道旧令牌会立即吊销。
6. **配网页的输入。** 全部严格校验：SSID 长度、密码长度、URL 只能是 https 加主机名，不能带路径、查询、用户名；沿用 `provision.py` 的同一套校验。

## 7. 失败模式（实现前要先写成测试）

Agent 端：
1. 授权码过期、已用、已取消、已烧毁、从没存在：兑换都失败，错误和耗时一致。
2. 第 6 次尝试：失败，且授权烧毁，即使第 6 次的码是对的。
3. 并发兑换同一个授权码：只有一个成功，令牌只发一个。
4. 兑换后重启 Agent：授权仍是已用，不能再兑换。
5. 权限范围、目标超出授权：拒绝。授权创建时就拒绝未知范围和空目标（沿用 `Store.pair` 的校验）。
6. 已配对的设备编号：没有 `replace` 就拒绝，且授权不消耗。
7. 限流器故障：拒绝。
8. 令牌不出现在日志、数据库明文、授权列表、错误信息里。
9. 有效秒数 0、负数、超过 300：拒绝。

设备端：
10. 配网码错误：不接受任何输入，错误 5 次关闭热点。
11. 热点 5 分钟到：关闭，输入的内容丢弃，什么都不保存。
12. 连不上 Wi-Fi、连不上 Agent、证书过期、主机名不符、证书链不对、兑换响应里的 CA 与配对包里的不是同一份：中止，旧配置原封不动。
13. 兑换成功但保存失败或读回不一致：不关闭配对状态，显示错误，旧配置不变。
14. 中途断电：要么是旧配置，要么是完整的新配置，不会有一半。
15. 已经配对且没有长按按键：热点不开。

## 11. 取 CA 这一步的调查结论（2026-10-28）

**决定：你选了 D1（配对包直接带 CA），已经实现（配对包版本 2）。** 下面保留调查记录，因为它说明了为什么不走 D2。

问题：设备只有配对包里的 CA 指纹，要先拿到 CA，才能做验证过的 TLS。第 4 节的做法是先用一个**不验证证书**的 TLS 连接去 `GET /api/v1/pairing/ca`。这在 ESP-IDF 6.0.2 里能不能安全地做？

### 结论

**没有安全的现成办法。**

1. **esp-tls 的默认行为是拒绝。** 客户端配置里没有任何验证选项（没有 CA、没有证书包、没有全局 CA 库）时，`esp_tls_mbedtls.c` 返回 `ESP_ERR_MBEDTLS_SSL_SETUP_FAILED`。唯一的出口是 `CONFIG_ESP_TLS_SKIP_SERVER_CERT_VERIFY`（依赖 `CONFIG_ESP_TLS_INSECURE`）。它是整个固件的编译期默认：开了以后，任何一处忘记配 CA 的客户端都会悄悄不验证。本项目的 `sdkconfig.defaults` 明确写了 `CONFIG_ESP_TLS_INSECURE=n`，这是 K1 的底线，不能开。
2. **`crt_bundle_attach` 钩子能做到，但要改基线。** `esp_http_client` 允许传一个函数，它能改写 mbedTLS 的配置（改成不验证，或装自己的验证回调）。可是这条路要 `CONFIG_MBEDTLS_CERTIFICATE_BUNDLE`，`sdkconfig.defaults` 也明确关了它（`=n`）。打开它要改基线文件（K7），并在固件里留一个故意不验证的函数。
3. **直接用 mbedTLS 代价最大。** mbedTLS 4 已经去掉了 `mbedtls_ssl_conf_rng`，要走 PSA；套接字读写、超时、错误都要自己写。
4. **握手里看不到 CA。** `tools/create_tls.py` 生成 RSA-2048 的 CA 和叶子证书，Agent 的 `tls_cert` 是叶子证书。设备在握手里只看到叶子，所以“核对证书链的根的指纹”做不到，只能单独去取 CA。

### 两个选项

| | D2：取 CA 并核对指纹（第 4 节原来的做法） | D1：配对包直接带 CA |
| --- | --- | --- |
| 做法 | 开证书包选项，写一个不验证的钩子，`GET /pairing/ca`，核对指纹，再用验证过的 TLS 兑换 | 配对包里放 CA 证书（DER，RSA-2048 约 760 字节）。设备直接用它做验证过的 TLS，一步到位 |
| 配对包长度 | 约 120 个字符 | 约 1090 个字符（RSA-2048），只能复制粘贴 |
| 固件里的不验证连接 | 有一个，要靠审查保证它不发送秘密 | 没有 |
| 基线文件 | 要改 `sdkconfig.defaults`（K7） | 不用 |
| Agent | 多一个公开接口（已实现） | 不需要这个接口（要删掉）；配对包改格式 |
| 失败环节 | 多一个（取 CA） | 少一个 |
| 主机测试 | 不验证的那一步没法在主机上测 | 全部可以在主机上测 |

**两者的信任是等价的。** 配对包本来就是信任根：它经过手机和热点，指纹和 CA 在同一个包里，能改一个的人也能改另一个。指纹只换来“包短”，不换来安全。D1 的信任来源和 USB 配对一样：CA 由人带过来。

### 建议：D1

理由：固件里不留任何不验证的连接，不动 `sdkconfig.defaults`，少一个公开接口，少一个失败环节，所有逻辑都能在主机上测。代价只是配对包变长，而你选“配对包复制粘贴”的原因就是不用手抄。

D1 做了什么（先写测试，再改）：
- 配对包升到版本 2：`DHP2.`，`02`，地址长度，地址，授权编号，授权码，CA 长度（2 字节），CA DER，校验。解码器检查 CA 恰好是一个 DER 序列：开头 `30`，长度用最短的定长形式（短形式、`81`、`82`），不接受不定长和三字节长度，后面没有多余字节，最大 2048 字节（比原来写的 1500 大，RSA-4096 的 CA 也放得下）。Agent 和设备的解码器用同一份向量（4 个合格、22 个不合格）。
- Agent：生成授权时放入 `pairing_ca` 的 DER；`GET /api/v1/pairing/ca` 和它的测试已删，另有测试保证现在唯一不需要登录的配对路由是兑换；`protocol/openapi.json` 没有这个路径了。
- 设备：解码器同步；`Session` 少 `FetchingCa` 阶段（`joined(true)` 直接进入兑换），`Why::PinMismatch`、`ca_fetched`、`pin_matches` 都删了；提交表单时由包里的 DER 生成 PEM，TLS 客户端只信这一份；兑换响应里的 CA 必须和包里的 CA 是同一份（DER 逐字节相同），否则按 `BadReply` 中止，旧配置不变。
- 第 8 节第 2 条已改成“配对包直接带 CA”。

如果你仍想要短包，选 D2：要改 `sdkconfig.defaults`，我会把钩子写成只在取 CA 时使用、不发送任何请求头和请求体里的秘密，并要求你复审那几十行代码。

## 12. 设备端接线方案

已选 D1。下面每一条都要先写失败模式和测试（能在主机上测的部分），再写代码，接线的代码要按 K1 复审。

1. **Wi-Fi 模式。** 现在 `core.cpp` 的 `network_start()` 只设 `WIFI_MODE_STA`。热点要 `WIFI_MODE_APSTA`，加 AP 网络接口，WPA2，密码来自 `Session::offer()`，最多 1 台设备连接。这改基线文件（K7）。
   **风险（要真机验证）：** 提交表单后，设备要连家里的 Wi-Fi。APSTA 下两个接口必须同一个信道，热点会跟着变，手机可能断开。所以结果显示在**设备屏幕**上，不依赖手机页面；页面在提交后提示“手机可能会断开”。
2. **配网页。** `esp_http_server`，HTTP（热点内没有 TLS），只绑定热点接口，只开 `GET /` 和 `POST /setup`，限制请求体大小（4 KiB：配对包最大约 2.8 KB，再加 Wi-Fi 名称和密码），`Cache-Control: no-store`，响应不回显任何秘密，不写日志。热点关闭时停止服务。
3. **兑换客户端。** 一次验证过的 `esp_http_client`：D1 用 `cert_der`（包里的 CA），保持主机名检查，不跟随重定向，响应上限沿用 16 KiB。把 esp-tls 的错误和 mbedTLS 的验证标志（过期、名称不符、不被信任）映射到 `Session` 的 `Tls`。Agent 的证书必须含配对包里的地址（IP 或主机名），这和 USB 配对的要求一样。
4. **`Sink` 的实现。** `current()` 和 `readback()` 用 `dh::secrets()`，`set_time()` 用 `dh::set_time_utc(utc, "manual")`，`commit()` 用 `dh::save_secrets()`，成功后同 USB 配对一样写 RTC 并 `network_reconfigure()`。
5. **随机数。** 热点密码和配网码用硬件随机数。ESP32 的随机数只有在射频子系统（Wi-Fi 或蓝牙）开着时才是真随机。所以 `Session::open()` 必须在 Wi-Fi 启动之后调用；未配置的设备如果 Wi-Fi 还没启动，要先启动它。
6. **按键。** BSP 没有按键定义（`BSP_CAPS_BUTTONS` 为 0）。BOOT 键通常接 GPIO0，但本板要用原理图核对；PWR 键据说接在电源芯片上，长按可能触发硬件关机，所以不选它（这一点我也没有核对）。**我没法从代码里确认，需要你给原理图，或确认用哪个键，真机验证前一律标“未验证”。**
7. **屏幕。** 把 `Session::offer()` 映射到 `dh::PairingInfo`（`ui_pairing_show`，已有）。配网页显示期间要保持亮屏，否则人看不到密码：界面定时器在配网页显示时刷新“最近活动”，夜间限亮等保护仍然生效（K5）。
8. **K1 复审清单。** 配网码、Wi-Fi 密码、授权码、令牌不进日志；配网页只在热点内可达；窗口、尝试次数、授权都有上限；保存只发生一次且完整；失败时旧配置原封不动；固件里没有不验证的 TLS（D1）。
9. **真机验证（等你说“刷”）。** 热点能连、配网页能打开、一次完整配对、Wi-Fi 信道切换时的表现、断电时旧配置不丢、10 分钟后热点确实关闭。

### 流程（对应第 4 节）

1. 没有存 Wi-Fi 的设备开机 8 秒后自动开一次；已存 Wi-Fi 的设备（配对过的，或只用软键盘设过 Wi-Fi 的）要长按按键 3 秒，或在屏幕上点“开始配对”。
2. 先启动 Wi-Fi 驱动（随机数只有射频开着才是真随机），再让 `Session` 生成热点密码和配网码，再开热点和配网页，屏幕显示配网页。
3. 手机连热点，在 `http://192.168.4.1/` 填配网码、Wi-Fi、配对包；手机的时钟随表单送来，设备用它设时间（证书要看时间）。
4. 页面立刻回答“已收到”，**然后**任务才去连 Wi-Fi（连接可能改变热点的信道，手机可能断开，所以结果不依赖手机页面）。
5. 连上以后，用配对包里的 CA 做验证过的 TLS，兑换授权码。
6. 成功：`Session` 通过 `dh::save_secrets` 保存一次，读回确认；然后关热点、停网页，Wi-Fi 任务用新配置重连。失败：旧配置原封不动。

### 失败模式和代码里怎么处理

| 编号 | 失败模式 | 处理 |
| --- | --- | --- |
| X1 | 页面被热点以外的人访问（局域网里的电脑访问设备的 Wi-Fi 地址） | `peer_in_hotspot`：只接受热点网段的地址，其余 403（G3） |
| X2 | 表单过大、格式错、重复、多余、带控制字符 | `parse_form`（G1）；Content-Length 先挡一道 |
| X3 | 配网码错 | `Session::enter_code`：5 次关闭热点（已有测试 E10）；页面只说“没有接受”，不说哪一项错 |
| X4 | 热点到时 | `Session::tick` 关闭；`teardown` 关热点、停网页、清内存里的表单 |
| X5 | 连不上 Wi-Fi、连不上 Agent、证书过期、主机名不符、链不对、返回的 CA 不是包里那份 | `joined(false)` 或 `redeemed(...)` 失败：旧配置不变，计入 5 次尝试（E12）；`tls_from_flags`（G2） |
| X6 | 保存失败或读回不一致 | `Session` 停在 SaveFailed，不关会话；任务最多重试 3 次，然后关闭，闪存不被反复写 |
| X7 | 配对期间 Wi-Fi 任务抢无线电 | `network_hold(true)`；关闭时 `network_reconfigure()` 让它按已存的配置恢复 |
| X8 | 未配置的设备配对失败后，Wi-Fi 驱动一直开着 | `radio_close` 在驱动是我们启动的时候关掉它 |
| X9 | 随机数不好 | 驱动启动后才允许取随机数；`Random::fill` 失败就不开（R1） |
| X10 | 机密进日志 | 本组件不打任何日志；`httpd` 的日志标签设为 NONE；`esp-tls`、`HTTP_CLIENT` 本来就是 NONE（app_main）；表单、包、密码在用完后清零 |
| X11 | 没有不验证的 TLS | 只有 `redeem_client.cpp` 一处 TLS，`cert_pem` 是包里的 CA，没有证书包，`CONFIG_ESP_TLS_INSECURE=n` 不变 |
| X12 | 按键引脚读到悬空或别的信号 | 内部上拉，悬空读“没按”；3 秒连续按下才算 |
| X13 | 用户在屏幕上点“取消配对” | 回调只置一个标志，任务收尾 |
| X14 | 提交后手机又提交一次 | `Session` 在 Joining 阶段拒绝（WrongPhase）；任务忙时页面等锁最多 0.5 秒，然后答“没有接受” |
| X15 | 断电 | 保存只发生一次，走 USB 配对同一条路径：要么旧的，要么完整的新的（E14） |

### 没有验证的，也就是真机上要看的

1. **按键。** 我用的是 GPIO0（BOOT）。板子的原理图没有核对，BSP 里没有按键定义。接错时的后果是长按打不开热点；悬空引脚读“没按”，所以不会误开。PWR 键我没有用：据说它接在电源芯片上。
2. **热点和 Wi-Fi 同时开。** 提交后设备去连家里的 Wi-Fi，两个接口要在同一个信道上，热点会跟着变，手机可能断开。
3. **内存。** 配对时 TLS（约 40 KB）、网页服务和界面同时在用。已配对的设备在长按配对时，Agent 客户端也可能同时有一条 TLS。堆够不够没有量过。
4. **手机能不能打开 `http://192.168.4.1/`。** 手机可能因为“这个热点没有互联网”断开或不愿用；404 会跳转到首页，是为了让手机的连通性检查弹出配网页，没有试过。
5. **Wi-Fi 驱动自己的日志**会打印连接的 Wi-Fi 名称（不是密码）。这在 USB 串口里能看到，和 0.3.x 现在连接已存的 Wi-Fi 时一样。
6. **结果在哪里看。** 屏幕没有结果行（界面没有改）。成功时首页顶栏的 Wi-Fi 和电脑图标会亮；失败原因读 USB 状态：`tools/provision.py --port … --status` 的 `pairing` 对象（`phase`、`why`）。
7. 已配对设备长按配对时会断开当前的 Wi-Fi 去连新的；失败时由 Wi-Fi 任务恢复，要在真机上看它是不是真的恢复了。
